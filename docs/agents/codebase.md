# LexScholar codebase guide (for agents)

Read this instead of exploring the repository. It covers where code lives, the patterns to follow and how to test it. Open a source file only once you know which one you need. If you add a module, a project or a pattern, update this guide in the same PR.

The F001 spec artifacts (`specs/001-research-workspace/`) are the historical record of how this was decided. You rarely need them; look up a specific decision in `research.md` by heading when a task asks about it.

## Functional-first patterns

**Domain: smart constructors returning `Result`.** No exceptions for expected failures.

```fsharp
module ProjectName =
    let create (name: string) : Result<ProjectName, ProjectNameError> =
        if String.IsNullOrWhiteSpace(name) then Error InvalidProjectName
        else
            let display = name.Trim()
            Ok { Display = display; Normalized = display.ToUpperInvariant() }
```

**Application: workflows take only the functions they need**, as a record of functions (`Store`) or function types (`Ports.fs`). No interfaces or DI container.

```fsharp
type Store =
    { ResolveWorkspace: unit -> Guid
      List: Guid -> ResearchProject list
      ActiveProject: Guid -> Guid option
      Create: Guid -> Guid -> string -> DateTimeOffset -> Result<ResearchProject, ProjectCreationError>
      Select: Guid -> Guid -> Result<unit, SelectionError> }

let select (store: Store) id = store.Select (store.ResolveWorkspace()) id
```

Errors are unions, often `[<RequireQualifiedAccess>]` (`Library.AssociationError.ProjectNotFound`).

**Server: composition at the edge.** Each `*Endpoints.map` builds the records from Infrastructure functions partially applied to the data directory, then maps routes and turns `Result` cases into HTTP responses:

```fsharp
let store : Projects.Store =
    { ResolveWorkspace = fun () -> ProjectRepository.resolveWorkspace directory
      List = ProjectRepository.list directory
      ... }
app.MapPut("/api/projects/{projectId:guid}/active", Func<Guid, IResult>(fun projectId ->
    match Projects.select store projectId with
    | Ok () -> Results.NoContent()
    | Error Projects.ProjectNotFound -> problem 404 "not_found" "Project not found")) |> ignore
```

Errors are ProblemDetails with a `code` extension (`problem` helpers in the endpoint modules, `Errors.problem` in middleware). Never put exception details or filesystem paths in a response.

**Client: Elmish with effects as data.** Each feature module has `Model`, `Message`, `Effect`, `initial` and a pure `update : Message -> Model -> Model * Effect option`. `App.fs` turns effects into HTTP calls (`Api` module) and results back into messages. Rules the existing modules follow:

- `Busy`/operation guards: messages are ignored while another operation runs (`| Create when model.Busy.IsNone -> ...`).
- Request numbers (`Library`, `Reader`): each fetch carries a counter, and responses for an older request are dropped.
- Results for a project that is no longer active don't change the current view.
- The client has its own small types; it doesn't reference Application. JSON parsing lives in `App.Api`.

**Sign-in button asset (F005).** `src/LexScholar.Client/wwwroot/chatgpt-logo-white.svg` is OpenAI's white ChatGPT logo, downloaded unmodified from `https://developers.openai.com/assets/siwc/sign-in-buttons/chatgpt-logo-white.svg` (listed on `https://developers.openai.com/siwc/website`, which also prescribes the label "Continue with ChatGPT" and the `data-oai-siwc-button` attribute). No licence text is published with it; it is used only as that page directs. The `.siwc-button` styles in `app.css` (black button, white logo) are ours.

**F006 onboarding (T014).** `App.State.Onboarding` is undecided until projects load, then starts only for an empty workspace. **F006 new summary language (T016, $153).** `Summarize.fs` requests Brazilian Portuguese regardless of source language in every single/map/combine prompt, including intermediate reductions, for both destinations. Stored summaries and source text are untouched. Application tests capture these instructions; fake replies do not establish real-model compliance.

**Single-origin onboarding lifecycle (T014 review fixes).** There is no cross-origin completion synchronization, handoff marker/query or pending automatic sign-in intent. All localhost entries normalize before workspace initialization, replacing the history entry and preserving query parameters. Explicitly reopening localhost cannot bypass numeric-loopback setup, even when projects already exist. Completion is one local session write and never navigates. Regressions cover interrupted initial navigation, Back/Forward before and after completion, localhost revisits while setup is active and completed, blocked completion-navigation paths, finish during account loading and later sign-out without unexpected authorization.

**F006 summary presentation (T021).** The document heading (filename, details and secondary `Abrir PDF` link) sits outside the separate white `.summary-request.card` or `.summary.card`. **F006 feedback replacement (T025).** `Summary.fs` keeps the durable version in `State.Shown` while its separate `Replacement` tracks consent, submission, polling, cancellation or failure. The transient `Feedback` draft uses T023's bounded `instruction` wire field and shared single/map/all-combine pipeline; no second backend input or persistence is added. Every replacement opens fresh consent, even for an already-confirmed account. `App.fs` POSTs `/summary/regenerate` and polls that replacement-aware GET after loading the durable version through the ordinary GET. Only a finished replacement swaps the visible version. Stop uses antiforgery-protected `POST /summary/cancel`, never legacy DELETE; cancellation of an in-flight POST drains its eventual answer with another cancel and blocks new replacements until outstanding cancels finish. Request/watch guards discard stale navigation results. Portuguese controls, failure messages and existing validated citation rendering are reused.

T025 review reconciliation: per-pair `Submissions` survive navigation; a late admission answer advances the watch to invalidate earlier discovery. `UncertainReplacements` survives navigation until nondestructive cancellation fences pending admission, including after a lost POST response. Failed cancellation offers Stop again, never fresh regeneration; a saved discovery alone cannot rule out delayed admission. Successful cancellation reconciles through `FetchReplacement`, adopting completion if it won the race. `Reconciling` permits draft editing but not submission, and discovery of the same saved version preserves that draft. Terminal `ReplacementFailed` allows explicit confirmed deletion; uncertainty does not.

T025 second-review guards: `ReplacementCancels` is a map keyed by project/document, and `replacementBusy` checks only the current pair's cancellation/admission. Inactive callbacks cannot hold the active pair in `Cancelling`. The wrapper initiates discovery only after a legacy result actually changed the model; ignored stale answers preserve consent and replacement state. Cancellation reconciliation uses legacy `Fetch` to hydrate an unloaded saved version first, then `FetchReplacement` once `Shown`.

## Request flow

**F002 metadata deletion (T012).** Internal `LibraryDeletion.removeMetadata` checks `LibraryDeletionRepository.hasItem` and fences the selected document's preparations/jobs under the shared workspace→registry boundary before calling the repository. `LibraryDeletionRepository.removeMetadata` takes the same mutation monitor and one SQLite transaction: recheck intent/storage key, remove associations (cascading stored summaries) and the document via `LibraryRepository.removeMetadata`, then record `metadata_removed` while retaining the journal storage key. It never removes originals or marks `deleted`. `removeMetadataWith` exposes association-removal, pre-commit and post-commit fault checkpoints for isolated tests. Exceptions are resolved using a fresh context/transaction: only the durable metadata-removed phase plus absence of document, associations and summaries proves success; otherwise retain intent and best-effort record sanitized `incomplete`/`storage_error`. Retries are idempotent. Production endpoints and startup do not compose this processing before T017; original removal and recovery remain T013/T014.

**F002 summary fencing (T011).** `SummaryJobs.Prepare` registers both ordinary and replacement HTTP preparations before body/vault/extraction awaits; `PrepareReplacement` remains a compatibility alias. Extraction and credential refresh receive cancellation linked to that preparation, and job registration checks its token even if an adapter ignores cancellation. `LibraryDeletion.admitFenced` takes the registry's workspace→registry boundary around journal admission (SQLite commit), then `FenceDocuments` cancels every selected document's preparations/jobs across projects, without deleting stored summaries. Failed/stale admission fences nothing. Only `LibraryDeletionEndpoints.mapForTests` composes this workflow until T017; production admission/retry/recovery remain disabled. `Endpoints.fs` supplies the registry's optional `isPending` capability to fence new preparations after intent without changing missing-association HTTP responses. `LibraryDeletion.fs` compiles after `SummaryJobs.fs` for this dependency. Host races use bounded extraction/credential/provider handshakes and retain job `Settled` tasks before fencing removes the jobs.

**F002 private export lifecycle (T006).** `LibraryExport.build` constructs a complete, rewound file-backed ZIP in private `exports/` (0700 directory, 0600 files, delete-on-close). It uses `DocumentStore.openOriginal`'s managed-key validation, checks recorded and actually copied lengths, and copies in cancellation-checked 81,920-byte chunks. Source open/length/read faults identify the document; archive write/finalization faults remain `export_failed`. `ExportFiles`/`buildWith` and `LibraryControlEndpoints.mapWithBuildForTests` are narrow deterministic test seams, not production routes. ASP.NET owns the returned stream through transfer completion/disconnect. `StorageCleanup.run` removes abandoned exports at startup under the workspace lock; export I/O/access failures leave private leftovers for next startup and report `ExportCleanupIncomplete` for a sanitized warning, without blocking the workspace or changing permissions. Export remains unmapped publicly until T008; race coverage belongs to T007.

**F002 journal foundations (T001).** `LexScholar.Application/LibraryControls.fs` defines deletion journal types only; it does not execute deletion. `WorkspaceDb.fs` and `Migrations/LibraryDeletions.fs` add `DeletionOperations` and `DeletionItems`. Items use `(OperationId, DocumentId)` identity, a partial unique index preventing multiple unfinished items for a document, and status/phase checks. Journal items retain their storage key independently of the library row. No F002 endpoints, deletion, recovery or coordination are enabled by this migration.

**F002 export snapshot (T002).** `LibraryExportSnapshot.withSnapshot` opens one deferred SQLite read transaction and establishes its snapshot before the callback. `read` captures library documents, associated projects, associations and decoded stored summaries in that transaction; `capture` is the ordinary one-call entry. The context must not escape the callback. `SummaryRepository.deserialize` is shared internally and still rejects unknown versions. The WAL-mode test commits changes from a second connection while the snapshot remains open; file-lifetime coordination and archive creation remain separate work.

**F002 summary export (T005).** `LibraryExport` renders captured stored summaries into association JSON plus UTF-8 `summaries/<project>/<document>.txt`, preserving citations and generation context without consulting live jobs. The same snapshot supplies document/project names and PDF paths. Unknown stored versions fail the entire build through the existing repository decoder; a running replacement exports the old saved version. Public export remains disabled until T008.

**F002 private export foundation (T004).** Application `LibraryExport.create` acquires the host's file lease around the infrastructure `LibraryExport.build` capability. The builder captures metadata through T002, streams originals into a private delete-on-close ZIP, and returns only a complete rewound stream. V1 document/project/association fields and UUID-only PDF entry paths are emitted; user filenames remain metadata. `LibraryControlEndpoints.mapForTests` is explicitly mapped by contract tests only, never by `Endpoints.map`. Public export stays unavailable until T008. T004 initially failed closed for stored summaries rather than omitting them; T005 replaced that temporary behavior with their structured/readable representation, as described above. T006/T007 own failure/lifecycle hardening and coordinated race verification.

**F002 deletion preview (T009).** `Application/LibraryDeletion.fs` validates selections and constructs a sorted SHA-256 revision over selected identities/names, project identities/names/roles and raw stored-summary content (including its version) plus generation time. Only summary presence enters the response. `Infrastructure/LibraryDeletionRepository.fs` uses the T002 snapshot transaction for all impact queries; `read` accepts that context for later atomic confirmation and deterministic interleaving tests. `Server/LibraryDeletionEndpoints.fs` exposes only `mapForTests`; isolated test hosts explicitly map the preview POST through `TestHarness.Start(configure = ...)`. Production `Endpoints.fs` does not call it. There is no confirmation, intent write, job cancellation or deletion in this slice.

**F002 confirmation admission (T010).** `LibraryDeletion.admit` compares selection/revision, distinguishes identical operation retries, operation conflicts and overlapping unfinished items. `LibraryDeletionRepository.admit` holds the host's mutation monitor and one immediate SQLite transaction across comparison and journaling every item, retaining names and storage keys without removing metadata or originals. `LibraryDeletionEndpoints.mapForTests` additionally maps confirmation; production confirmation/retry remain unmapped. `LibraryRepository` rejects pending-item association, role and removal writes; host callers already hold T003 coordination. `Endpoints.fs` wraps the existing summary save/delete capabilities with `unlessPending` and makes pending pairs unavailable to new registry admission, without changing `SummaryRepository.fs`. Running/preparing job cancellation and send fencing remain T011; this slice does not process journal items or enable startup recovery.

**F002 coordination (T003).** `LibraryCoordination` supplies one host-owned mutation monitor and an asynchronous, cancellation-aware file lease. `Program.fs` registers it once; `Endpoints.fs` gives the same instance to `SummaryJobs`, `LibraryEndpoints` and `DocumentEndpoints`. Summary registry operations take the mutation monitor before the registry lock; association/role changes and the import database insert take the mutation monitor. Import commit takes the file lease before checking duplicates/promoting/inserting, without holding the registry lock. `ImportDocument.create` retains its isolated default for existing callers; the host uses `createCoordinated`. This establishes a boundary for later export/deletion work, not deletion or a complete race-proof deletion lifecycle. `TestHarness.Start(pdfValidation = ...)` allows deterministic import validation handshakes.

The coordination `FileWait` event fires after an asynchronous file lease wait has been queued; the host import test uses it to observe the actual shared lease boundary.
`PdfText.extractPagesWith` accepts a callback after opening the verified stream; the T003 host test reads a fixture byte and holds that real stream open while exercising registry and simulated deletion progress. Ordinary `extractPages` uses a no-op callback.

T023 privacy follow-up (PR #133): `summarizeWithInstruction` discards all service `ErrorStatus` prose for nonblank instructed calls before failure/job-state retention, preserving status numbers and recognized categories. This prevents refusal echoes from retaining user instructions; default uninstructed failure behavior is unchanged.

**F006 optional first-summary instruction (T023, owner extension).** `Domain.SummaryInstruction` shares the 2,000-character limit/blank normalization. `Summary.Instruction` is an in-memory draft editable only at Idle; `SendWithInstruction` freezes it through consent (Cancel retains it; navigation/job acceptance clears it). `SummaryStatus.requestBodyWithInstruction` serializes it separately from consent fields. `SummaryEndpoints.Body` validates optional `instruction` and the 16 KiB body cap (`400 invalid_instruction`), then passes it into either background path. `Summarize.summarizeWithInstruction` wraps the shared completion capability to add separate user input to every single/map/combine call without changing existing blank/default prompts, language or citation validation. Raw instructions are not separately persisted or logged; generated summaries can reflect them. See F006 `contracts/summary-instruction.md`. No recent history or saved instruction metadata. T024/T025 reuse this workflow with a separate replacement lifecycle.

**F006 regeneration backend (T024).** `SummaryJobs.Start`/`StartWith`/`StartFailed` accept `regenerate = true`: a saved row is required, but does not block explicit replacement; a running job still wins. The endpoint scopes `PrepareReplacement` before its first await; `Cancel`, destructive `Stop` and association removal invalidate these admissions under the same lock used by job registration. No cancelled preparation can later start a job, including after extraction/plan refresh. `Cancel` drops only the transient operation, unlike destructive `Stop`. `POST .../summary/regenerate` shares ordinary validation/confirmation; `GET .../summary/regenerate` explicitly exposes replacement progress/failure. Legacy base GET/ordinary POST and status listing instead show the durable finished version, so their destructive Stop/Close actions cannot target replacement work. `POST .../summary/cancel` never deletes that version. `GET .../summary/saved` reads it directly under the lock. Existing atomic `SummaryRepository.save` replaces it only on successful completion. No schema/client changes. `SummaryEndpoints.PageExtraction` is an injectable capability (default `PdfText.extractPages`); `TestHarness.Start(summaryExtraction = ...)` holds extraction for deterministic admission-race tests. Contract: `specs/006-summary-first-portuguese/contracts/summary-regeneration.md`.

Client `update` returns an `Effect` → `App.fs` runs the HTTP call (`Api.*`) → host middleware (`HostSecurity.useSecurity`: error handler, Host and Origin checks, antiforgery on unsafe methods) → endpoint → Application workflow → Infrastructure functions → SQLite or files → `Result` → HTTP status and JSON → `App.fs` maps it to a `Message` → `update`.

Startup order (`Program.fs`, don't reorder casually): configuration → data-directory lock → `WorkspaceDb.initialize` (migrations) → host security config → build → `StorageCleanup.run` → middleware → static assets → endpoints.

Import (`ImportDocument.create`, `POST /api/documents`): stage at most MaxBytes + 1 bytes → validate (size, `%PDF-`, PdfPig, SHA-256) → serialized commit: duplicate check by SHA-256 then byte comparison → promote (fsync, read-only, move without overwrite) → insert row → always discard staging. `201` for new, `200` for reused bytes.

## Recipes

**Add an endpoint.**
1. Domain types and rules first, if any, with tests in `tests/LexScholar.Domain.Tests`.
2. Workflow in Application taking a `Store` record or capability functions; add the store field it needs.
3. Infrastructure function(s) in the matching repository; schema changes need a migration (below).
4. Map the route in the matching `*Endpoints.fs` (or a new module, registered in `Endpoints.fs` and the `.fsproj` before `Endpoints.fs`). Update `contracts/http-api.yaml` of the active feature.
5. Contract test in `tests/LexScholar.Server.Tests/*ContractTests.fs` (see Tests).

**Add a schema change.** Migrations are handwritten F# with raw SQL (`migration.Sql`): copy `Migrations/Documents.fs`, give it a `Migration("<timestamp>_<Name>")` later than the last one, update `WorkspaceDbModelSnapshot.fs` and the row types in `WorkspaceDb.fs`, register the file in the `.fsproj` after the existing migrations, and add a schema test (`tests/LexScholar.Infrastructure.Tests/*SchemaTests.fs`).

**Add a client feature.** A new `Model`/`Message`/`Effect`/`update` module (or extend one), registered in the client `.fsproj` before `App.fs`; wire its effects and view in `App.fs`. Test `update` first (state tests); add a browser journey only for what state tests can't show.
