# Research: Summary first, in Portuguese (F006)

## R11 — Brazilian Portuguese for all new summaries ($153, T016)

- **Decision**: Owner clarification makes Brazilian Portuguese the output language of every new summary, whatever the source language. Replace the source/majority-language instruction in all three shared `Summarize.fs` prompts: single call, per-chunk map, and combine (both intermediate and final reductions). Both plan and configured-service paths use this workflow. This supersedes F003's language decision and F006's former F007 deferral; R7's unchanged backend refers to destination handling, not this later prompt correction.
- **Why**: One instruction change per prompt is the smallest fix, with no language setting, detection, extra translation request, dependency or migration. Source text, citations, JSON parsing, storage and existing summaries remain unchanged.
- **Alternatives**: Translate on display (changes historical summaries); translate in a second model call (extra cost and risk to citations); keep source language until F007 (contradicts the owner's confirmed requirement).
- **Verification**: Capture instructions for English, Portuguese and mixed-language single-call inputs and for chunk/intermediate/final calls. Reuse the restart regression proving stored English text and provenance survive without service requests. Fake replies verify instructions and pipeline behavior, not actual model language compliance; the real-plan smoke check must confirm Portuguese output.

Decisions for [plan.md](plan.md). Each has the decision, why, and the alternatives considered (constitution VI). The look comes from [mockups/README.md](mockups/README.md).

## R10. Owner-approved onboarding remediation (T014, $14z, $151)

- **Decision**: track onboarding independently of project count. It starts after the first successful project-list load finds no projects, remains through creation/import/sign-in, and ends only on explicit skip/finish. Retain its active/finished flag in same-origin browser `sessionStorage` across reload and the same-tab authorization return. Normalize every localhost app entry to `127.0.0.1` on the same port before loading projects or reading setup state, replacing the history entry and preserving query parameters. Only the OAuth callback origin owns workspace/setup state. The three numbered cards follow screen 05, with the owner's additional completion action.
- **Why**: project creation is step one, not completion. A session flag keeps a subsequent reload or ChatGPT callback from dropping the remaining optional steps without introducing server storage, migrations or auth changes.
- **Lifecycle**: completion is a local session write with no navigation. There is no cross-origin completion protocol or pending automatic sign-in intent. Every localhost visit normalizes before workspace initialization, regardless of project count. Reopening localhost while setup is active therefore consults the same active flag, and revisiting after explicit completion consults the same finished flag. Back/Forward and reload retain that single session decision.
- **Alternatives**: project-count-only detection caused $151; an in-memory flag loses setup on authorization navigation; a persistent server marker adds storage and an endpoint for a session-only concern; `localStorage` outlives the setup session unnecessarily and also cannot cross origins. Sign-in-time handoff required fragile source/destination completion synchronization and automatic sign-in intent; review exposed interruption windows, so that design was removed. Canonicalizing only an empty workspace still let a localhost revisit bypass active setup after project creation; that exception was removed too. Existing workspace addresses now normalize, but their data, active project, account and workflows are unchanged. No authentication/callback change or server storage is needed.
- **Limits**: no credentials or document details go into the flag. A new session with existing projects bypasses onboarding; a new session with none offers it again. When browser storage is unavailable, setup works in memory, but a reload/authorization return with an already-created project may enter the workspace. Project creation does not auto-select or auto-associate imports; those existing behaviors remain unchanged.

## R1. Opening a PDF at a page in a new tab (FR-002, FR-003, SC-001)

- **Decision**: "Abrir PDF" and every citation are plain links (`<a target="_blank" rel="noopener">`) to the document's existing content URL (`GET /api/documents/{id}/content`, served inline with range support). A citation adds the PDF open parameter `#page=N`, where N is the first page it cites. Nothing new on the server for the happy path.
- **Why**: The reader frame already used `{contentUrl}#page=N` (F003 research, "citation shows the page"). Firefox's built-in viewer (pdf.js) and Chromium's viewer both honour `#page=N` on a top-level PDF document, which is what a new tab is. F001 and F003 checked this by hand in both browsers. A link opens a new tab on every click, so the frame's navigation counter is no longer needed. The page number comes from the citation's validated pages (F003), so a link cannot point at another document or page (Principle I).
- **How a browser test confirms it**: Playwright's bundled browsers don't render PDFs in tests: headless Chromium has no PDF viewer, and Playwright's Firefox runs with pdf.js disabled, so a PDF navigation becomes a download in both. The journey tests therefore check what the app controls, in both browsers:
  1. each citation is a link whose `href` is the opened document's content URL plus `#page=N`, with `target="_blank"`, and its text is `p. N` or `pp. N–M`;
  2. clicking it opens a new page (`context.WaitForPageAsync`) that requests that document's content URL, and only that document. The fragment never reaches the server, so the test reads the popup's URL, or the link's `href` if the download aborts the navigation. T004 records which of the two applies in each browser.
  That the viewer shows page N is checked by hand in Firefox and Chromium (quickstart, step 3), as in F001 and F003.
- **Alternatives**: a `/documents/{id}/page/{n}` route that redirects to `content#page=n` (one more route, same fragment, and nothing more for a test to check); rendering pages to images on the server (it rebuilds the reader the spec removes); running pdf.js inside the app (a new dependency, and again an in-app reader); enabling pdf.js in Playwright's Firefox through a preference so a test can read the page number from the viewer (it depends on the viewer's internals and works in one browser only; rejected for now, possible later if the manual check proves unreliable).

## R2. The missing-file page (FR-007)

- **Decision**: The content endpoint keeps its JSON problem response (`503 document_unavailable`, `404 document_not_found`) for API callers. When the request is a browser navigation, it answers with the same status and a short Portuguese HTML page instead. A navigation is a request whose `Accept` header includes `text/html`: browsers send that when opening a tab, and `fetch` doesn't by default. The page has the title "Documento indisponível", one sentence ("O arquivo deste documento não foi encontrado ou não pode ser lido. O registro na biblioteca e os projetos não foram alterados."), and no technical text, path or code. It is a fixed string in `ReaderEndpoints.fs` (renamed to `DocumentEndpoints.fs`, R6) with the app's colors, served with `Content-Type: text/html; charset=utf-8` and `X-Content-Type-Options: nosniff`.
- **Why**: With links in new tabs, the server's answer is all she sees. One check on `Accept` keeps the API's problem codes stable (contract tests unchanged) and adds no route. The library record and associations are untouched: the endpoint only reads, so F001 FR-017 still holds.
- **Alternatives**: the client checks the content (`HEAD`) before opening a tab (rejected in clarify, option B; popup blockers also reject tabs opened after an `await`); a separate HTML route for the tab (two URLs for the same document, and the citation links would need it too); serving the client app at a route that shows the error (it loads the whole WASM app to show one sentence).

## R3. Where the Portuguese texts live; server failures in Portuguese (FR-009, FR-012)

- **Decision**: All interface text lives in one new client module, `src/LexScholar.Client/Texts.fs` (`module LexScholar.Client.Texts`), compiled first: named values for the FR-012 glossary and every label, plus functions for texts with parameters (`pages 3 = "p. 3"`, `pageRange 4 6 = "pp. 4–6"`, document counts, the confirmation sentence with the file name and page count). The client already turns every problem `code` into a union case (`Library.parseFailure`, `SummaryStatus.failureOfCode`, `Reader.parseFailure`). Those unions are defined in `Library.fs`, `Projects.fs` and `Summary.fs`, which compile after `Texts.fs`, so the messages for them live in a second small module, `src/LexScholar.Client/FailureTexts.fs`, compiled after `SummaryStatus.fs` and before `App.fs`: one function per union (`FailureTexts.library`, `FailureTexts.project`, `FailureTexts.summary`, …) that gives the Portuguese message, built from `Texts` values. `Texts.fs` itself references no client type. An unknown code is already a `RequestFailed`/`ServiceFailed` case, which shows "Algo deu errado. Tente novamente." The server's `detail` and `title` are never shown (they aren't today either). The server keeps its English `title`/`detail` and its codes.
- **Why**: It is the smaller change. The mapping from code to case already exists and is tested, so only the strings change. The API's codes stay stable, and server tests don't change. With one module, the glossary is checkable in one file. Tests can use the same values (R5).
- **Alternatives**: the server sends Portuguese `detail` (two places hold texts, every endpoint and its tests change, and the client still needs a fallback for unknown codes); resource files (`.resx`) with `IStringLocalizer` (built for many languages, while the spec says no language choice; it adds satellite assemblies to the WASM download and globalization settings); keeping the strings in place in `App.fs` (no single place to check the glossary, and tests would repeat literals).

## R4. Date and time format (FR-010)

- **Decision**: `Texts.dateTime (value: DateTimeOffset)` formats `value.LocalDateTime` with the fixed pattern `dd/MM/yyyy HH:mm` and `CultureInfo.InvariantCulture`, giving `14/11/2026 18:54`. It replaces the single use today (`App.fs`, `yyyy-MM-dd HH:mm`). It has a state test with a fixed value.
- **Why**: The pattern has no culture-specific parts with the invariant culture, so it gives the same output whatever the browser's language, with no globalization data in the WASM app. Local time is what she reads; the conversion is the browser's time zone, as today.
- **Alternatives**: `CultureInfo("pt-BR")` (needs `BlazorWebAssemblyLoadAllGlobalizationData` or ICU data in the download, and the culture's patterns could change); formatting in JavaScript with `Intl.DateTimeFormat("pt-BR")` (JS interop for one string).

## R5. How browser tests find elements once the text is Portuguese

- **Decision**: Journeys select by **role and accessible name**, and the names come from `Texts` (Browser.Tests already references the client project): `page.GetByRole(AriaRole.Button, Name = Texts.summarize)`, not a literal. Lists and regions get an accessible name (`aria-label`) or a heading, so tests scope with `GetByRole(AriaRole.List, Name = Texts.focusedSources)` / `GetByRole(AriaRole.Region, Name = Texts.summary)` instead of CSS classes. Citations are `GetByRole(AriaRole.Link, Name = "p. 3")`. `data-testid` only where no role or name fits, expected for: the main area (`data-testid="main"`) and a document's row in the project list (to filter it by file name). A few assertions keep exact Portuguese literals on purpose, to check the glossary (the generated label, "Continuar com o ChatGPT", the date format), because a test that only reads `Texts` can't catch a wrong text.
  The ~70 English selectors aren't rewritten in a separate pass. Each slice migrates the tests of the screen it changes, and T001 adds the helpers (`button`, `link`, `region` taking `Texts` values) to `tests/LexScholar.Browser.Tests/Ui.fs`.
- **Why**: Roles and names are what she and assistive technology use, and Playwright recommends them. `Texts` values make tests follow a wording change without edits, while the literal checks still guard the glossary.
- **Alternatives**: `data-testid` everywhere (tests stop checking that the controls are labelled at all); Portuguese literals everywhere (each wording fix breaks many tests); CSS classes, as many tests do today (they break with the redesign's markup).

## R6. What goes with the reader (FR-001, FR-008)

- **Decision**:
  - Removed: `src/LexScholar.Client/Reader.fs` (opening, content check, page navigation, iframe), the reader card in `App.fs` (heading "Reader", "Open in new tab", "Close", the `iframe`), `Api.checkContent`, `tests/LexScholar.Browser.Tests/ReaderStateTests.fs`, `ReaderJourneyTests.fs`, `ReaderApiTests.fs` (after moving whatever still applies: the role-change and stale-project cases go to the new document-list tests, the content-endpoint cases to the server contract tests if not already there). Their shared journey helpers move to `Ui.fs`.
  - Kept: `GET /api/documents/{id}/content` (now also the link target and the HTML page of R2) and `PATCH /api/projects/{p}/documents/{d}` (role change). The server module `ReaderEndpoints.fs` is renamed `DocumentEndpoints.fs`, since there is no reader any more.
  - New: the "opened document" (which document of the active project fills the main area) moves into `Library.fs` as `Opened: Guid option`. It is closed when the project changes or the document leaves the project, the rules `Reader.followLibrary` had. `Summary.followReader` becomes `followOpened`. The role change, with its one-at-a-time guard, stale-project rule and `RefreshProject`, moves into `Library.fs` too, and is offered on each row of the project's document list (FR-008), as "Tornar fonte principal" / "Tornar fonte de referência".
- **Why**: The content check existed so the frame wouldn't show a raw error. The new tab now gets the R2 page, so the check has no purpose. The library state already owns the project's documents, so the opened document and the role change belong there; no new module is needed.
- **Alternatives**: keep `Reader.fs` as a renamed "Opened" module (a module for one field and two rules); keep the content check before opening a document (it delays the summary for a file the summary doesn't need, and the clarification moved the error to the tab).

## R7. Only her ChatGPT plan in the interface (FR-005)

- **Decision**: The client stops offering a destination choice. `Summary.fs` keeps the `Destination` type, but the client asks only for `Destination.Plan` and treats a configured service in `GET /api/summary/destinations` as absent for new requests. When she isn't signed in, the request to summarize offers "Continuar com o ChatGPT" and nothing else, with no settings-file explanation. The texts for `NotConfigured` and the settings file are removed. Historical summary provenance is an explicit exception to hiding configured-service UI: retain `generated.ServiceHost`, model, date and existing context (Principle IV, FR-014), never replacing the host with a generic label or attributing a configured-service summary to her ChatGPT plan. Server code, contract and settings file are unchanged.
- **Why**: It is the smallest change that meets FR-005: the server still accepts both destinations, and only the client's request and texts change. If the server has a summary for the pair from either destination, it is still shown (F004).
- **Alternatives**: removing the configured destination from the server response (it changes the backend, which the spec keeps).

## R8. Look: tokens and fonts

- **Decision**: `app.css` is rewritten around the README's tokens as CSS custom properties (`--accent: #0E6E80`, …) and the three-column layout of screen 06 (projects, the project's documents, main area), with the top bar ("LexScholar", breadcrumb, "Conectado ao ChatGPT", account menu). Inter and Source Serif 4 are **served locally** from `wwwroot/fonts/` as WOFF2 files, one variable font each, both under the SIL Open Font License. The license texts go next to them, and their provenance is recorded in `codebase.md`, like the ChatGPT logo. Fallbacks: `system-ui, sans-serif` and `Georgia, serif`. `index.html` gets `lang="pt-BR"` and the loading text "Carregando LexScholar…". The F007 parts of the screens are not built: "Gerar novamente", "Sua instrução" and the instruction field, the "Recentes" suggestions, flags on points, "Este resumo foi útil?".
- **Why**: Fonts from Google's CDN would make the browser contact Google on every start. That goes against keeping her work local (Principle II), and the app would look wrong offline. Variable fonts keep it to two files (about 300 KB each, served once and cached).
- **Alternatives**: Google Fonts link (external request, see above); system fonts only (no new files, but the summary's serif reading text and the mockups' look are lost; acceptable fallback if the owner prefers fewer files); a CSS framework (a new dependency for about 150 lines of CSS).
