# F002 local HTTP and UI contract

All routes remain same-origin on loopback under existing Host/Origin protections. Every POST requires the existing `X-CSRF-TOKEN`. JSON names below are normative for planning; errors follow existing ProblemDetails with safe codes and no filesystem paths or research text.

## Export

`POST /api/library/export` has no body. A complete constructed archive returns `200 application/zip` with attachment disposition. Empty library: `409 empty_library`. A required missing, unreadable, wrong-length, or failed-read PDF: `409 document_unavailable` with safe document ID and display name. Other construction/storage failure: `500 export_failed`; no partial ZIP response. Unknown stored summary version: `500 export_failed`, no omission. Failed transfers are not client success. User sees Portuguese explanation, including no in-app restoration. Archive staging is private and cleaned after transfer/disconnect or on restart.

## Preview and confirm

`POST /api/library/deletions/preview` body `{ "documentIds": ["uuid", ...] }` (nonempty unique IDs); `200` returns `{ "documents": [{ "id", "name", "projects": [{ "id", "name", "role", "hasSummary" }] }], "revision": "opaque" }`. Unknown IDs: `404 document_not_found`; malformed/duplicate/empty selection: `400 invalid_selection`. No side effects. UI displays all documents, projects and summary impact, permanence and external-copy limitations, with Cancel and Delete.

Client generates and retains an `operationId` before submitting confirmation, so even a lost response has a lookup key. `POST /api/library/deletions` body `{ "operationId": "uuid", "documentIds": ["uuid", ...], "revision": "opaque" }`. Under coordination recompute impact and compare; changed impact returns `409 impact_changed` with fresh preview, creates no intent and requires confirmation again. Otherwise durably record the operation and return `202` with operation ID; processing may continue independently of the request. Repeating the same operation ID and same selection returns the existing operation; reuse for a different selection is `409 operation_conflict`. Unknown/malformed IDs return errors before any intent. Any concurrent pending deletion of the same document produces `409 deletion_in_progress`, with no partial admission. A lookup returning 404 while the original request may still be in flight does not prove non-admission: the client retains the same ID and retries only the identical confirmation, whose admission is serialized and idempotent. A failed lookup is likewise unknown, never success or permission for a new operation.

`GET /api/library/deletions/{operationId}` returns `200` `{ "operationId", "status": "running" | "complete" | "partial", "items": [{ "documentId", "name", "outcome": "deleted" | "not_completed", "reason": null | "pending" | "storage_error" }] }`. `complete` only when every item is deleted. `running` when recovery/processing is active; `partial` when work is incomplete and not active. Unknown ID `404`. `GET /api/library/deletions` lists retained operations so another tab or restart can reconcile them. Retry incomplete work with `POST /api/library/deletions/{operationId}/retry`; it does not authorize new document selections. Acknowledge completed operations with `POST /api/library/deletions/{operationId}/acknowledge`; reject acknowledgement while any item is incomplete. On restart, recovery runs before serving and failed items remain listed. Return sanitized errors; no destructive retry on stale previews or changed selections.

UI reports every item and never represents partial as complete. Deletion does not erase previous downloads, backups, original imports or content already sent elsewhere; secure physical erase is not promised. Existing association removal remains separate.

Retry returns `202 { "operationId": "uuid" }`, including an already-running or completed retained operation; concurrent retries coalesce and never add selections. Acknowledge returns `204`, or `409 deletion_incomplete` for unfinished items (`409 deletion_in_progress` while the processor is active). Lookup, retry and acknowledge of an unknown/acknowledged UUID return `404 operation_not_found`. The list response is an array of the same operation objects as lookup. Storage read/write failures return an error, never an empty successful list or an inferred completed result.

Through T016 these routes are mapped only by explicit isolated test hosts. Production confirmation/retry remain unmapped and startup deletion remains disabled until T017 enables the complete controls together.
